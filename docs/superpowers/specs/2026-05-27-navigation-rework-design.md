# 导航重构设计

状态：待实现前评审

## 背景

当前 Web 导航只有 `大纲 / 章节` 两栏，但实际工作流已经分成多个层次：

- 大纲内部包含多个阶段，但这些阶段现在和编辑、审查、锁定动作挤在同一个界面里。
- `chapter_outline` 是从大纲到章节正文的桥梁，不适合继续混在普通大纲阶段里。
- 生成、修订、锁定的语义没有完全分开，用户很难判断当前阶段是否还能锁定、为什么不能锁定。

结果就是流程看起来很多，实际操作路径很短，用户会卡在“下一步该点什么”上。

## 目标

1. 把一级导航改成三项：`大纲 / 章节大纲 / 章节正文`。
2. 所有阶段都拆成独立的 `生成`、`修订`、`锁定` 动作，不再共用一个模糊按钮。
3. 锁定状态完全由后端状态控制，前端只展示后端返回的可用动作和原因。
4. `章节大纲` 作为独立一级导航，按卷动态展示章节大纲列表。
5. 在每个阶段界面显式显示当前状态、是否可锁定、不可锁定原因。

## 非目标

- 不改写小说创作图的核心逻辑。
- 不引入新的数据库或持久化层。
- 不新增“解锁”流程，本次只处理生成、修订、锁定的前向操作。
- 不重做 Web 整体视觉，只调整信息架构和动作模型。

## 总体方案

采用三层结构：

1. **一级导航**：`大纲 / 章节大纲 / 章节正文`
2. **工作区内部视图**：每个一级导航内部再按功能切页
3. **动作条**：每个阶段都提供 `生成 / 修订 / 锁定` 三个独立动作，动作可用性来自后端

其中，`章节大纲` 不再只是大纲里的一个普通阶段页，而是一个独立工作区。它的内部按卷切换，左侧显示卷列表，右侧显示当前卷的章节大纲内容和状态。

## 信息架构

### 1. 大纲

只承载：

- `direction`
- `worldbuilding`
- `characters`
- `story_flow`
- `volume_outline`

这个工作区保留阶段列表，但不再把 `chapter_outline` 放进来。每个阶段卡片只负责展示阶段摘要、状态和动作。

### 2. 章节大纲

独立一级导航，承载：

- 按卷查看章节大纲
- 按卷生成章节大纲
- 按卷修订章节大纲
- 按卷锁定章节大纲

这一区域的核心对象是“卷”，不是“阶段按钮”。它适合单独做，因为它本身已经是大纲和章节正文之间的一层编排。

### 3. 章节正文

保留现有三个二级视图：

- 批量生成
- 已生成章节
- 总体审查

这部分不变，只调整导航入口位置。

## 阶段动作模型

所有阶段统一使用三种动作：

- `生成`：首次建立或重建阶段内容
- `修订`：基于当前内容做定向修改
- `锁定`：确认当前阶段内容进入下一阶段

UI 上不再使用一个合并按钮表达“生成/修订”。用户必须清楚地看到两个独立动作。

### 动作可用性

每个阶段 payload 由后端返回统一的动作状态：

```json
{
  "status": "options_ready",
  "action_state": {
    "can_generate": true,
    "can_revise": true,
    "can_lock": false,
    "lock_reason": "仍有 2 个待确认问题"
  }
}
```

原则：

- `can_generate`：阶段未锁定且没有后端错误时可用。
- `can_revise`：阶段已有内容或已有草案时可用。
- `can_lock`：只有后端判断满足锁定条件时才可用。
- `lock_reason`：不可锁定时必须给出原因。

前端不自己推断这些状态，只渲染后端结果。

## 章节大纲工作区

`章节大纲` 需要单独建模为“卷视图”：

- 左侧：卷列表，动态来自 `volume_outline` 和 `chapter_outline` 的卷规格
- 中间：当前卷的章节大纲内容
- 顶部：当前卷状态、生成 / 修订 / 锁定按钮、锁定原因

### 卷数据

后端需要返回：

- `volume_specs`
- `current_volume_index`
- `completed_volumes`
- `volume_statuses`
- `selected_volume`

其中 `selected_volume` 至少包含：

- `index`
- `label`
- `status`
- `summary`
- `content`
- `can_generate`
- `can_revise`
- `can_lock`
- `lock_reason`

### 卷级锁定

`章节大纲` 的锁定不是“整个阶段一次性锁完”，而是当前卷满足条件后允许锁定。未完成的卷显示为不可锁定，并说明缺少什么。

当所有卷都锁定后，章节大纲工作区整体显示为完成态。

## 后端契约

本次建议复用现有文件存储与图逻辑，但扩展 Web 服务的 payload 语义：

### 1. 大纲阶段 payload

每个普通大纲阶段都返回：

- `stage`
- `label`
- `status`
- `summary`
- `content`
- `pending_questions`
- `action_state`

### 2. 章节大纲 payload

章节大纲单独返回卷级数据，而不是简单阶段文本。

### 3. 动作接口

建议把动作语义显式化为：

- `POST .../generate`
- `POST .../revise`
- `POST .../lock`

如果后端内部仍复用同一个执行器，也要在请求层区分 `generate` 和 `revise`，避免前端继续猜语义。

### 4. 状态判定

后端负责判断：

- 当前阶段是否已有内容
- 当前阶段是否满足修订条件
- 当前阶段是否可锁定
- 当前卷是否可锁定

如果前端状态过期，后端必须返回拒绝结果和原因，不能静默执行。

## 交互流程

### 大纲阶段

1. 用户在左侧选择一个阶段。
2. 右侧显示阶段标题、状态、动作条。
3. 用户点击 `生成` 或 `修订`。
4. 后端执行后返回最新状态。
5. `锁定` 只有在 `can_lock=true` 时可点。

### 章节大纲

1. 用户进入 `章节大纲`。
2. 左侧自动列出所有卷。
3. 用户选择某一卷。
4. 右侧显示当前卷内容、状态、动作条和锁定原因。
5. 当当前卷锁定后，切换到下一卷或保持当前卷只读，具体由后端返回的 `current_volume_index` 决定。

### 章节正文

保留原有批量生成、章节列表、总体审查，不改动其交互含义。

## 错误处理

- 后端拒绝锁定时，前端必须显示 `lock_reason`。
- 后端执行失败时，保留当前文本，不清空编辑器内容。
- 任何动作失败后，进度日志仍保留最近一次的失败原因，方便用户回看。
- 关闭/切换阶段时，如果有未完成请求，旧响应不能覆盖当前选中内容。

## 测试计划

需要补三类测试：

1. **导航结构测试**
   - 验证一级导航只有 `大纲 / 章节大纲 / 章节正文`
   - 验证 `chapter_outline` 不再出现在普通大纲阶段列表里

2. **动作状态测试**
   - 验证每个阶段都有独立的 `生成 / 修订 / 锁定`
   - 验证 `can_lock=false` 时按钮禁用且显示原因

3. **章节大纲卷级测试**
   - 验证卷列表按后端返回动态生成
   - 验证当前卷能切换、能显示状态、能控制锁定
   - 验证卷级 payload 会把 `volume_specs` 和 `selected_volume` 一起返回

## 选择理由

选这个方案的原因是：

- 信息架构和用户心智一致。
- `章节大纲` 的卷级结构单独出来后，流程不会再挤在一个阶段页里。
- 动作和锁定完全由后端控制，前端不会再凭 UI 文案猜下一步。
- 复用现有存储和大部分工作流，改动集中、风险可控。

## 约束

- 不新增解锁流程。
- 不把“修订”重新合并回“生成”。
- 不允许前端自行判断锁定资格。
- 不在大纲侧继续暴露 `review_lock` 作为普通阶段导航项。
